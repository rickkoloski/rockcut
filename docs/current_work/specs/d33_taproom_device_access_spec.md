## 1. Problem Statement

The taproom has tablets behind the bar. Matt wants them signed in all the time
so any staff member can glance at the schedule and read the staff channels
and, later, use taproom tools without signing in personally.

A normal account won't do:

- **A shared personal password is dangerous.** Whoever knows it can sign in
  from anywhere, and changing it signs out every tablet.
- **A department membership grants too much.** Memberships are what grant
  things by default in this app: audiences, notifications, module access,
  claiming, time off, posting. Posting from a shared login is anonymous posting.
- **Signing in alone grants things too.** A user with no memberships can still
  change their password, create their own time off and availability, rotate a
  calendar feed, subscribe to push, read departments and see published shifts
  (Rick, file #4026 §2).

D33 adds a **device** kind of account, closed on every route and every decision
unless explicitly allowed, and **pairing** that gives each tablet its own
revocable token.

## 3. Requirements

### 3.1 The device account

- [ ] `users.kind`: `"person"` (the default, every existing row) or `"device"`.
- [ ] `users.home_department_id`: required when `kind = "device"`, null
      otherwise. It decides which department channel and nav section the
      device sees (`bar`).
- [ ] Invariants, enforced in the changeset **and** tested:
  - never `is_owner`;
  - **no memberships**: `set_memberships` refuses a device (422);
  - `schedulable = false`, `must_reset_password = false`;
  - a **random, unusable** `password_hash` (the column is NOT NULL);
  - `POST /api/session` refuses `kind: "device"` explicitly.
- [ ] **The four user-listing fixes** (Rick's count against D31):

  | Query | Fix |
  |---|---|
  | `Accounts.list_roster` (grid rows) | exclude devices (`schedulable: false` plus a `kind` filter) |
  | `Messaging.recipients("all")` → `active_users_query` | exclude devices, or the tablet gets All-staff notifications |
  | `Accounts.list_users_for` (Users & Roles) | exclude devices; they're listed under Shared devices |
  | shift / template assignee | reject a device id in validation |

- [ ] Owners create, rename, deactivate and delete the device account from
      **Admin → Shared devices**.
- [ ] Every create, pair, revoke and deactivate is written to the audit log and
      shows in the owner's User change log.

### 3.2 Pairing and device tokens

- [ ] **`device_tokens` table:**
  - `user_id` (the device account);
  - `name` ("Taproom iPad 1");
  - `token_hash`;
  - `paired_by_id`;
  - `last_seen_at`, `revoked_at`;
  - timestamps.
- [ ] **Pairing codes:**
  - 8 characters, with no look-alike characters;
  - **single use**, and expire after **10 minutes**;
  - stored **hashed**;
  - generated by an owner or a manager of the device's home department (Q2)
    from **Shared devices → Pair a tablet**.
- [ ] **Rate limit:** at most 5 wrong codes per IP per 10 minutes. A small ETS
      counter is enough; the app has no rate limiting today.
- [ ] **On the tablet:**
  - the login screen has **"Set up as a shared device"**;
  - the person enters the code and a tablet name;
  - `POST /api/device_tokens` exchanges the code for a random token prefixed
    `dev_`, which is shown to the tablet once and stored only as a hash.
- [ ] **`AuthPlug`:**
  - recognizes the `dev_` prefix and looks the token up on every request;
  - rejects it if it's revoked or the account is inactive, so **revocation
    takes effect on the next request**;
  - updates `last_seen_at` at most once a minute;
  - has no expiry: revocation is the control.
- [ ] **Shared devices page:** each tablet with its name, who paired it, when,
      last seen, and **Revoke**.
- [ ] **Signing out on a tablet** revokes its token. The tablet then needs a new
      code, and the UI warns first: "A manager will need to pair this tablet again."
- [ ] The device never registers for push.

### 3.3 Gate 1: the router (deny by default)

- [ ] A `DeviceGate` plug in the `:authenticated` pipeline rejects device
      tokens with **403** on every route that isn't in a `:device_allowed`
      scope. A route added later stays closed to devices unless someone opens it.
- [ ] **Allowlist (Rick §6):**

  | Route | Device | Notes |
  |---|---|---|
  | `GET /api/me`, `GET /api/session` | ✅ | returns `kind: "device"` and device capabilities |
  | `DELETE /api/session` | ✅ | revokes this tablet's token (§3.2) |
  | `GET /api/departments`, `GET /api/positions`, `GET /api/roster` | ✅ | read only; the schedule needs them |
  | `GET /api/shifts`, `GET /api/shifts/:id` | ✅ | **published only**, via the device clause in `Authz.scope` |
  | `GET /api/schedule_events` (D32) | ✅ | published only |
  | `GET /api/channels`, `GET /api/channels/:key/messages` | ✅ | **All-staff + Taproom only** |
  | `POST /api/channels/:key/read`, `GET /api/messages/unread_count` | ✅ | unread markers work because the device is a real user row |
  | `POST /api/channels/:key/messages` | ❌ | no anonymous posting |
  | everything else: time off, availability, claiming or changing shifts, templates, notifications, preferences, push, calendar feeds, password, users, memberships, owner activity, brewery | ❌ | |
  | future taproom components | per component | each adds its own router **and** `Authz` entry |

### 3.4 Gate 2: `Authz` (deny by default)

- [ ] The **first** `can?/3` clause, above the owner shortcut and the other
      rules that bind owners, is
      `can?(%User{kind: "device"} = d, action, resource)`. It sends every
      decision to a device allowlist (`Authz.Device`) that ends in a catch-all `false`.
- [ ] `scope/3` has a matching first clause: devices get published records only.
- [ ] The device allowlist covers:
  - reading published shifts and events, positions, departments and the roster;
  - `:view` on channels `all` and `dept:<home>`, and marking them read;
  - `:access` to `{:module, <home>}`.
- [ ] `:post` on any channel is **explicitly** denied, even though the
      catch-all would deny it, so the intent is on record and tested.
- [ ] Capabilities for a device: `kind: "device"`,
      `modules: [<home>, "schedule"]`, no management flags.
- [ ] Any `kind` check lives in `Authz` (`authz_boundary_test.exs` passes).

### 3.5 Tablet UI

- [ ] The app bar shows a **"Shared device · Taproom"** chip. No notification
      bell and no profile or password menu.
- [ ] Nav: Home, View Schedule, Taproom, Messages (All-staff, Taproom).
- [ ] In a channel, the message box is replaced by "Shared devices can read but not post."
- [ ] A direct URL to anything else shows D31's "not available" page, never an
      empty table with an "Add" button.
- [ ] **Channel URLs (backlog 3939, from the D31 DEV pass):** a channel key the
      user can't see (for example `/messages/managers` as `floater`, or any key
      for the device other than All-staff and Taproom) redirects to `/messages`.
      It must not render an empty channel with a message box, keep polling
      into 403s, or fail a send silently. A 403 on send shows an error. This
      applies to **every** user, not only the device. Add a Playwright
      negative-persona spec and run the revert-and-rerun check.
- [ ] **Personal sign-in on a tablet** (Rick §5): a staff member can sign into
      their own account on a paired tablet, for example to request time off.
      After **N idle minutes** (§6 Q1), the tablet signs them out and returns
      to the device session. The device token is kept aside, not overwritten.

### 3.6 Tablet setup (operations, not code)

- [ ] `docs/process/taproom_tablet_setup.md`:
  - pair the tablet;
  - turn on iPad **Guided Access** (or Android screen pinning), so a customer
    can't leave the app or open developer tools and copy the token;
  - what to do with a lost tablet (Revoke).

### 3.7 Test support

- [ ] Synthetic persona **`taproomDevice`** (`kind: "device"`, home `bar`) in
      the DEV/local seed, with a mint and pair path in `Release` and
      `mix rockcut.synthetic.token taproomDevice`.
- [ ] **Negative matrix (ExUnit):** every route in the router × `taproomDevice`
      gives the expected result: the allowlist passes and **everything else is
      403**. It's generated from the router, so a new route fails the test until
      someone classifies it.
- [ ] **Authz matrix:** every D29 decision × `taproomDevice` → the expected
      allow or deny. The D31 parity suite stays **untouched** and green.
- [ ] **Token tests:** revoked → 401; inactive account → 401; a used, expired or
      wrong code → refused; the 6th wrong code → rate-limited; password login as
      a device → refused.
- [ ] **Playwright:** device-persona specs for the nav, read-only channels,
      blocked URLs, and pair → revoke.

### Non-functional

- [ ] **Security:**
  - tokens are opaque, hashed and revocable, with last seen visible;
  - codes are single use, short-lived, hashed and rate-limited;
  - the device can never become an owner, manager or member;
  - both gates deny by default.
- [ ] **No behavior change for people.** Every existing persona behaves exactly
      as before; the parity suite proves it.
- [ ] **Survives the later RBAC phases.** When roadmap Phases 2–6 replace the
      hardcoded rules with a level resolver and then roles stored as data, the
      device allowlist carries over as a **system role for `kind: "device"`**
      (Rick, file #4026 Appendix A), and a device can never be given a person's
      role. The device matrix tests (§3.7) are what prove it didn't change.
      Recorded in `planning/rbac_configurable_authorization_roadmap.md` and
      backlog tasks 3849–3853.

|---|---|---|---|---|
| S1 | `owner` | Admin → Shared devices | no device yet | Creates "Taproom tablets" (home: Taproom). It isn't in Users & Roles, the roster or any assignee picker. The change log shows the create. |

| S4 | anyone | tablet login | used, expired or wrong code | Refused with a clear message. The 6th wrong code in 10 minutes is rate-limited. |

| S6 | `taproomDevice` | nav | signed in | Sees Home, View Schedule, Taproom and Messages (All-staff, Taproom). No Scheduler, Time off, Availability, Admin, Brewery, bell or profile. |

| S8 | `taproomDevice` | Messages → All-staff, then Taproom | both have messages | Reads both. No message box. `POST /api/channels/all/messages` returns 403. Managers isn't listed, and its URL returns 403. |
| S9 | `taproomDevice` | typed URLs `/scheduler`, `/time_off`, `/availability`, `/users`, `/brands` | signed in | The "not available" page each time. The matching API calls return 403. |

| S11 | `owner` | Shared devices | two tablets paired | Revokes "Taproom iPad 1". Its next request returns 401 and it goes back to setup. iPad 2 keeps working. |
| S12 | `owner` | Shared devices | device account deactivated | Every tablet is signed out on its next request. |
| S13 | `bartender1` | tablet → personal sign-in | device session active | Requests time off as themself. After N idle minutes the tablet returns to the device session without re-pairing. |
| S14 | `owner` | Users & Roles | editing a person | The device can't be picked as a member, owner or assignee anywhere. The API rejects a device id as an assignee (422). |

## 5. Out of Scope

- Taproom components (D34+). Each adds its own router and `Authz` entries.
- A staff PIN on edits, to attribute them to a person (deferred to the first
  editable component).
- A Party / party-type data model (Rick, Appendix A). Revisit only if Rockcut
  goes multi-tenant. `users.kind` is the right size for now.
